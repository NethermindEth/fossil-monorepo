# PitchLake Verifier Contract

This document provides a comprehensive overview of the PitchLake Verifier contract - the StarkNet smart contract that verifies RISC Zero Groth16 proofs for PitchLake option pricing calculations.

## Overview

The PitchLake Verifier contract (`PitchLakeVerifier`) is a StarkNet smart contract that provides cryptographic verification of zero-knowledge proofs generated by the Fossil proving service. It uses the Garaga library to verify Groth16 proofs on the BN254 elliptic curve, ensuring that option pricing calculations (reserve price, TWAP, max return) were computed correctly off-chain before executing them on-chain.

**Contract Name**: `PitchLakeVerifier`
**Interface**: `IPitchLakeVerifier`
**Location**: `starknet-contracts/pitchlake-verifier/`
**Version**: 0.1.0

## Key Features

- **RISC Zero Proof Verification**: Verifies Groth16 proofs generated by RISC Zero zkVM
- **BN254 Elliptic Curve**: Uses BN254 curve via Garaga library for efficient verification
- **Journal Decoding**: Extracts and validates computation results from proof journals
- **Vault Integration**: Automatically calls back to PitchLake vaults with verified results
- **Access Control**: Owner-only functions for updating verifier address
- **Upgradeability**: Contract can be upgraded by owner via OpenZeppelin Upgradeable component
- **Event Emission**: Emits detailed verification events with all pricing data

## Architecture

### Verification Flow

```
RISC Zero Proof (Rust Proving Service)
    ↓
StarkNet Transaction → verify_proof()
    ↓
Groth16 Verifier (Garaga) → verify_r0_groth16_proof_bn254()
    ↓ (Cryptographic Verification)
Journal Extraction
    ↓
decode_journal() → PitchLake Journal
    ↓ (Parse financial metrics)
Vault Callback → IVault::fossil_callback()
    ↓
Event Emission → PitchlakeProofVerified
```

### Contract Components

```
PitchLakeVerifier (Main Contract)
├── Risc0Groth16VerifierBN254 (Groth16 verification)
│   └── UniversalECIP (Elliptic curve operations)
├── OwnableComponent (Access control)
└── UpgradeableComponent (Contract upgrades)
```

### Data Flow

1. **Proof Generation**: Rust proving service generates RISC Zero proof with journal
2. **Submission**: Proof submitted to `verify_proof()` with job request metadata
3. **Cryptographic Verification**: Garaga library verifies Groth16 proof
4. **Journal Parsing**: Extract financial metrics from journal bytes
5. **Vault Callback**: Call PitchLake vault with verified results
6. **Event Emission**: Emit verification event with all data

### Function Details

#### verify_proof

```cairo
fn verify_proof(
    ref self: TContractState,
    proof: Span<felt252>,
    pitchlake_job_request: PitchLakeJobRequest,
)
```

**Purpose**: Verifies a RISC Zero Groth16 proof and executes a callback to the PitchLake vault with the verified results.

**Flow**:
1. Extracts proof data (first element is metadata, rest is proof)
2. Calls Groth16 verifier to verify proof cryptographically
3. Decodes journal from proof output
4. Serializes job request and results
5. Calls vault's `fossil_callback()` with verified data
6. Emits `PitchlakeProofVerified` event

**Parameters**:
- `proof`: Calldata from RISC Zero proof generation (includes hints and proof data)
- `pitchlake_job_request`: Metadata about the proof (vault address, timestamp, program ID)

**Reverts**: If proof verification fails with error 'Failed to verify proof'

#### update_verifier_address

```cairo
fn update_verifier_address(
    ref self: TContractState,
    new_verifier_address: ContractAddress,
)
```

**Purpose**: Updates the underlying Groth16 verifier contract address (owner only).

**Use Case**: When a new version of the Groth16 verifier is deployed or configuration needs updating.

### Journal

```cairo
#[derive(Drop, Debug, Copy, PartialEq, Serde)]
pub struct Journal {
    data_8_months_hash: [u32; 8],                    // 32 bytes - Hash of 8 months of data
    start_timestamp: u64,                            // 8 bytes - Data range start
    end_timestamp: u64,                              // 8 bytes - Data range end
    reserve_price_start_timestamp: u64,              // 8 bytes - Reserve price calc start
    reserve_price_end_timestamp: u64,                // 8 bytes - Reserve price calc end
    reserve_price: felt252,                          // 32 bytes - Calculated reserve price
    twap_start_timestamp: u64,                       // 8 bytes - TWAP calc start
    twap_end_timestamp: u64,                         // 8 bytes - TWAP calc end
    twap_result: felt252,                            // 32 bytes - Time-weighted average price
    max_return_start_timestamp: u64,                 // 8 bytes - Max return calc start
    max_return_end_timestamp: u64,                   // 8 bytes - Max return calc end
    max_return: felt252,                             // 32 bytes - Maximum return value
    floating_point_tolerance: felt252,               // 32 bytes - Floating point tolerance
    reserve_price_tolerance: felt252,                // 32 bytes - Reserve price tolerance
    twap_tolerance: felt252,                         // 32 bytes - TWAP tolerance
    gradient_tolerance: felt252,                     // 32 bytes - Gradient tolerance
}
```

**Purpose**: Contains all verified computation results from the RISC Zero proof

**Key Fields**:
- `data_8_months_hash`: SHA256 hash of the input data used in calculations (integrity verification)
- `reserve_price`: Calculated option reserve price (primary pricing metric)
- `twap_result`: Time-weighted average price over the specified period
- `max_return`: Maximum potential return for the option
- Tolerances: Error bounds for various calculations (fixed-point arithmetic)

### Journal Encoding Format

The journal is encoded as a byte array with the following structure:

```
Offset  | Size    | Field
--------|---------|---------------------------------------
0-31    | 32      | data_8_months_hash (8 × u32)
32-39   | 8       | start_timestamp (u64)
40-47   | 8       | end_timestamp (u64)
48-55   | 8       | reserve_price_start_timestamp (u64)
56-63   | 8       | reserve_price_end_timestamp (u64)
64-133  | 70      | reserve_price (hex string: 4 + 2 + 64)
134-141 | 8       | twap_start_timestamp (u64)
142-149 | 8       | twap_end_timestamp (u64)
150-219 | 70      | twap_result (hex string: 4 + 2 + 64)
220-227 | 8       | max_return_start_timestamp (u64)
228-235 | 8       | max_return_end_timestamp (u64)
236-305 | 70      | max_return (hex string: 4 + 2 + 64)
306-375 | 70      | floating_point_tolerance (hex)
376-445 | 70      | reserve_price_tolerance (hex)
446-515 | 70      | twap_tolerance (hex)
516-585 | 70      | gradient_tolerance (hex)
```

**Hex String Format**: `[4 bytes length][2 bytes "0x"][64 bytes hex chars]`

Example: `66, 0, 0, 0, 48, 120, ...` = Length 66, "0x", then 32 bytes as hex

## Groth16 Verification

### Using Garaga Library

The contract uses the [Garaga](https://github.com/keep-starknet-strange/garaga) library for efficient Groth16 proof verification on StarkNet.

**Dependency**:
```toml
# Scarb.toml
garaga = { git = "https://github.com/keep-starknet-strange/garaga.git", branch = "main" }
```

**Key Components**:
- `IRisc0Groth16VerifierBN254`: Interface for RISC Zero-specific Groth16 verification
- `UniversalECIP`: Elliptic curve inner product operations contract
- Precomputed constants: Verification key, pairing lines, trusted setup parameters

### Verification Process

```cairo
// 1. Deserialize proof with hints
let fph = deserialize_full_proof_with_hints_risc0(full_proof_with_hints);

// 2. Validate curve points
groth16_proof.a.assert_on_curve(0);
groth16_proof.b.assert_on_curve(0);
groth16_proof.c.assert_on_curve(0);

// 3. Compute journal digest
let journal_digest = journal_sha256(journal);
let claim_digest = compute_receipt_claim(image_id, journal_digest);

// 4. Multi-scalar multiplication (MSM) for public inputs
let vk_x = ec_safe_add(T, msm_result, 0);

// 5. Pairing check
let check = multi_pairing_check_bn254_3P_2F_with_extra_miller_loop_result(
    G1G2Pair { p: vk_x, q: vk.gamma_g2 },
    G1G2Pair { p: groth16_proof.c, q: vk.delta_g2 },
    G1G2Pair { p: groth16_proof.a.negate(0), q: groth16_proof.b },
    vk.alpha_beta_miller_loop_result,
    precomputed_lines.span(),
    mpcheck_hint,
    small_Q,
);
```

**BN254 Curve**: Uses the Barreto-Naehrig curve with 254-bit prime for efficient pairing operations

**Verification Key**: Includes alpha, beta, gamma, delta points and precomputed miller loop results

### Rust Service Components

#### 1. Proof Verifier Configuration

```rust
// Location: proving-service/crates/message-handler/src/proof_verifier.rs

pub struct ProofVerifierConfig {
    pub risc0_config: Risc0Config,
    pub verifier_contract_address: String,
    pub verify_onchain: bool,
    pub job_request: Option<PitchLakeJobRequest>,
}

impl ProofVerifierConfig {
    pub fn from_env() -> Result<Self> {
        let verifier_contract_address = std::env::var("PITCHLAKE_VERIFIER_CONTRACT")
            .map_err(|_| eyre!("PITCHLAKE_VERIFIER_CONTRACT required"))?;

        let verify_onchain = std::env::var("VERIFY_PROOFS_ONCHAIN")
            .map(|v| v.to_lowercase() == "true")
            .unwrap_or(false);

        Ok(Self {
            risc0_config: Risc0Config::default(),
            verifier_contract_address,
            verify_onchain,
            job_request: None,
        })
    }
}
```

#### 2. Onchain Verification

```rust
// Location: proving-service/crates/message-handler/src/proof_verifier.rs

async fn verify_proof_onchain(
    &self,
    calldata: Vec<Felt>,
    verifier_address: &str,
    job_request: PitchLakeJobRequest,
) -> Result<Felt> {
    // Load StarkNet configuration
    let config = load_starknet_config()?;

    // Create provider
    let provider = StarknetProvider::new(config)?;

    // Convert to starknet-handler PitchLakeJobRequest
    let starknet_job_request = starknet_handler::account::PitchLakeJobRequest {
        vault_address: job_request.vault_address,
        timestamp: job_request.timestamp,
        program_id: job_request.program_id,
    };

    // Verify proof onchain
    let tx_hash = provider
        .verify_proof_onchain(verifier_address, calldata, starknet_job_request)
        .await?;

    Ok(tx_hash)
}
```

#### 3. Complete Verification Pipeline

```rust
// Location: proving-service/crates/message-handler/src/proof_verifier.rs

async fn generate_and_verify_proof(
    &self,
    timestamp_ranges: ProofTimestampRanges,
    config: ProofVerifierConfig,
) -> Result<ProofVerificationResult> {
    // Step 1: Generate RISC0 proof
    let risc0_result = self.generator
        .generate_proof_with_data(timestamp_ranges, config.risc0_config)
        .await?;

    // Step 2: Verify onchain (if configured)
    let onchain_tx_hash = if config.verify_onchain {
        let job_request = config.job_request.clone()
            .ok_or_else(|| eyre!("job_request required for onchain verification"))?;

        Some(self.verify_proof_onchain(
            risc0_result.calldata.clone(),
            &config.verifier_contract_address,
            job_request,
        ).await?)
    } else {
        None
    };

    Ok(ProofVerificationResult {
        risc0_result,
        onchain_tx_hash,
        total_time_ms: total_start_time.elapsed().as_millis() as u64,
    })
}
```

## Security

### Cryptographic Security

**Groth16 Proofs**: Industry-standard zero-knowledge proof system with:
- Cryptographic soundness: Computational hardness assumptions (elliptic curve discrete log)
- Proof size: Constant size (~200 bytes) regardless of computation complexity
- Verification time: Constant time verification (efficient on-chain)

**BN254 Curve**: Secure pairing-friendly curve with:
- 128-bit security level
- Efficient pairing operations
- Widely audited and battle-tested

**RISC Zero Integration**: Leverages RISC Zero's security guarantees:
- Receipt claim verification (image ID + journal digest)
- SHA256 journal hashing
- Trusted setup from RISC Zero zkVM

### Access Control

**Owner-Only Functions**:
- `update_verifier_address()`: Only owner can change verifier contract
- `upgrade()`: Only owner can upgrade contract implementation

**OpenZeppelin Components**:
- `OwnableComponent`: Industry-standard ownership pattern
- `UpgradeableComponent`: Secure upgrade mechanism
- Owner set during construction, transferable via OwnableComponent

### Data Validation

**Curve Point Validation**:
```cairo
groth16_proof.a.assert_on_curve(0);
groth16_proof.b.assert_on_curve(0);
groth16_proof.c.assert_on_curve(0);
```

**Journal Integrity**:
- SHA256 hashing of journal ensures data integrity
- Receipt claim verification links journal to RISC Zero program
- Bounds checking in journal parsing prevents buffer overflows

**Proof Verification**:

### Timestamp Normalization

**Hour Boundary Alignment**: All timestamps are normalized to hour boundaries (3600 second intervals) to ensure consistency:

```rust
// Location: proving-service/crates/starknet-handler/src/account.rs
const HOUR_IN_SECONDS: u64 = 3600;

fn normalize_timestamp(timestamp: u64) -> (u64, bool) {
    let normalized = (timestamp / HOUR_IN_SECONDS) * HOUR_IN_SECONDS;
    let was_normalized = normalized != timestamp;
    (normalized, was_normalized)
}
```

**Security Benefit**: Prevents timestamp manipulation attacks and ensures data consistency with hourly average fee data.

### Vault Callback Security

**Callback Validation**:
- Only verified proofs trigger vault callbacks
- Vault address comes from trusted job request
- All data passed to vault is cryptographically verified

**Reentrancy Protection**: Single call pattern with no state changes after external call

### Audit Considerations

**Key Security Properties**:
1. Proof verification cannot be bypassed
2. Journal data matches verified computation
3. Only verified data reaches vaults
4. Owner privileges are minimal and well-defined
5. Upgrade mechanism follows best practices

**Potential Risks**:
- Garaga library dependency (external code)
- Verifier key configuration (must match RISC Zero setup)
- Owner key compromise (can update verifier or upgrade contract)

## Performance Characteristics

### Gas Costs

**Verification Gas**: Dominated by Groth16 verification operations
- Pairing checks: Most expensive operations
- Multi-scalar multiplication: Moderate cost
- Journal decoding: Relatively cheap
- Vault callback: Variable (depends on vault implementation)

**Optimization**: Garaga library uses Cairo-optimized elliptic curve operations for efficiency

### Proof Size

**Calldata Size**: RISC Zero proof calldata is ~2600 felt252 elements
- Groth16 proof: ~8 field elements (A, B, C points)
- Hints: Majority of calldata (for efficient verification)
- Journal: Variable size based on data (typically 400-600 bytes)

**Constant Verification Time**: Regardless of computation complexity in guest program

### Verification Time

**On-Chain**: Single transaction, constant time
- Independent of RISC Zero guest program complexity
- Only depends on proof structure (constant for Groth16)

**End-to-End Timing** (Example from tests):
```
RISC0 Proof Generation: Variable (seconds to minutes)
Proof Submission: ~1-2 seconds
Groth16 Verification: <1 second
Total: Dominated by proof generation time
```

## Troubleshooting

### Common Issues

**1. Proof Verification Fails**
```
Error: 'Failed to verify proof'
```
**Causes**:
- Invalid proof data (corrupted during transmission)
- Mismatched verifier key (RISC Zero guest program changed)
- Invalid journal digest (data integrity issue)

**Solutions**:
- Regenerate proof with correct parameters
- Verify verifier contract address matches deployment
- Check RISC Zero guest program hash matches expected value

**2. Journal Decoding Errors**
```
Error: Index out of bounds / Invalid hex string
```
**Causes**:
- Journal format mismatch (RISC Zero guest program changed output format)
- Corrupted journal data

**Solutions**:
- Verify guest program output format matches decode_journal expectations
- Check journal byte array length (should be ~585 bytes)

**3. Vault Callback Fails**
```
Error: Callback to vault reverted
```
**Causes**:
- Vault not ready to receive callback
- Invalid job request data
- Vault state inconsistency

**Solutions**:
- Verify vault address is correct and deployed
- Check vault state allows callbacks
- Review vault logs for specific error
